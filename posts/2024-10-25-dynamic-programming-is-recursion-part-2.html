Newcomers to Haskell are often flumoxed by laziness. And perhaps they are more flumoxed when trying to use laziness and persistent data structures to implement classical algorithms.

In this article, I’m going to go over an implementation of the Lengauer-Tarjan algorithm to find dominators in control-flow graphs, which is a problem that comes up often when building compilers. The classic algorithm as presented in the paper has several subtleties that make an imperative implementation finicky. For example, the order of node processing matters, and the final pass requires a union-find algorithm. I’ll show you why Haskell’s laziness basically lets us elide all of those concerns and lets us essentially write out the algorithm as it is presented.

Firstly, some background and intuition.

# Control-flow Graphs

A control-flow graph is a graph that shows how control in a computer program can proceed from one compilation unit to another. These units can be modules, functions, or even blocks within functions. Starting at any node \(A\), a sequence of nodes \(\( A, A_1, A_2, A_3, \ldots, A_k, B \)\) is called a path from \(A\) to \(B\) if \((A, A_1) \in E\), \((A_k, B) \in E\), and \((A_i, A_{i+1}) \in E\), for all \(1 \leq i \leq k - 1\), where \(E\) is the set of edges in a control flow graph \(G\).

A common operation on control flow graphs is to find dominators of all nodes. Given a root node \(R\) (or a set of root nodes), node \(D\) is said to dominate a node \(N\) if all paths from the root to \(N\) must go through \(D\). In a control flow graph, this means that if \(N\) has been reached, then \(D\) must have somehow been involved. For example, the following is our if-statement graph, but now annotated with the dominators.

The naive algorithm for finding dominators involves initially setting all nodes as dominator to every other node (except the root), and then propagating dominators down control flow edges (taking the intersection each time) until no further changes are made. This is an \(O(n^2)\) algorithm, where \(n\) is the number of nodes.

The Lengauar-Tarjan algorithm is almost linear (\(O(m \log n)\) where \(m\) is number of edges and \(n\) is number of vertices).

## Algorithm sketch

The Lengauer-Tarjan algorithm is a two-part algorithm. In the first part, we establish potential dominators of nodes called ‘semi-dominators’, and then in the second part, we iteratively bump semi-dominators who are not true dominators until all dominators are accounted for.

The first part (the calcuation of semi-dominators) is straightforward, and we will approach it first. The first step here is to perform a DFS starting at the root (entry) node and then numbering each node we encounter. Call this number the vertex index.

If we select only those paths that were traversed during the DFS, we compute a spanning tree of the control flow graph. In a tree, the dominators are trivial, it’s just all ancestors. Thus, in this tree, due to the numbering by DFS, every node must have a parent with an index less than theirs.

If we take the spanning tree of our graph, then there’s only one path from the root to every vertex, and the path goes in strictly increasing order of index. However, in the full graph, this is not necessarily the case: for any node \(n\), there may be a path from its ancestors to \(n\) where the indices are greater than \(n\). Such paths may represent alternate dominators, since their existence suggests that there are ways to reach this node that are not in the spanning tree. We define

[sdom(w) = \min\{v \| \text{there is a path } v, v_1, v_2, , v_k, w, \text{s.t. v_i > w for 1 \leq i \leq k \}]

The set of paths which satisfy the condition is called the set of semi-dominator paths. Note that \(sdom\) is defined for all nodes. For any node \(n\) with parent \(p\) in the spanning tree, the path \(\\{p, n\\}\) is always a semi-dominator path. Thus, in the trivial case, the semi-dominator is the immediate parent.

I’ll give you one guess as to why we call these node assignments ‘semi-dominators’. To complete the algorithm, we still have to do some more work. The semi-dominators are potentially correct, but may be wrong. Recall that they represent only one alternative path to the node, but there could be others, and the dominator we calculate must dominate all the paths.
